Godot 双维度探索与轻战斗游戏 Demo
正式题面 v1.0 · 2026-10-17 · 从零开发条件

任务
使用 Godot 4.5.1 stable，制作一个原生 2D 与原生 3D 都能完整通关的短流程游戏 Demo。游戏结合探索解谜与轻战斗，具有真实背包、本地数据库、完整玩家 UI，以及草地、风场、水面和三套风格表现。两种维度共享同一个世界进度、背包、任务与存档。交付可离线运行的独立工程。

目标体验为约 5–8 分钟的单关卡。题材、主线目标、关卡布局、美术、角色与敌人造型、UI 样式和转场方式由你设计。以完整、清楚、可重复游玩为目标，不靠强制等待填充时长。


开发起点与运行环境
- 从空白 Godot 工程开始制作。本题不提供已有游戏工程、场景、Shader、素材或参考实现；全部必做项均须在本题内完成并验证。
- SQLITE_DEPENDENCY.zip 仅包含官方 godot-sqlite v4.6 插件、Windows x86_64 的 debug/release DLL、接口文档与许可证。
- 使用 Godot 4.5.1 stable（Windows x86_64），引擎由测试环境预装；通过环境变量 GODOT4_EXE 提供本机引擎可执行文件路径。
- user:// 使用本工程独立目录，具体命名由你设置并记录。
- UI 样式、2D/3D 转场、题材、关卡细节与原创机制由你设计。

一、必须完成的玩法
1. 从主菜单新游戏进入，具有可理解的主目标、探索、资源获取、环境解谜、战斗、检查点和明确终局。
2. 至少两种规则不同的环境谜题；至少一种让风、草地或水体实际参与游戏规则。关键物品、机关与任务进度有关联。
3. 玩家可移动、冲刺或闪避、攻击、交互、使用技能/物品，具有生命、冷却或资源限制。碰撞、镜头、攻击方向和状态反馈合理。
4. 至少两类攻击或行为规则不同的敌人。具备巡逻/待机、发现/追击、攻击前摇、命中、受伤与死亡等必要状态。敌人和投射物遵守碰撞/遮挡规则。
5. 具有可验证的失败与重试。检查点的保留/回滚规则明确，不因关键物品丢失、消耗或机关状态错误造成无法继续。

二、真正的双维度与共享状态
1. 2D 使用 Node2D 与 canvas_item 等原生路径，3D 使用 Node3D 与 spatial 等原生路径，两种模式各自具备完整控制、交互、战斗和通关能力。
2. 共用关卡逻辑、物品定义、任务、敌人状态和持久化数据。呈现、镜头与物理适配可以不同，但游戏规则与进度语义一致。
3. 能切换维度并继续当前进程。位置、生命、背包、装备、已开宝箱、已拾取物、敌人、门机关和任务状态不得意外重置；不重复伤害、掉落或奖励。
4. 2D/3D 转场的形式自行设计。要求切换状态清楚、输入处理合理、世界状态连续，转场期间的暂停/时间规则明确。
5. 切换美术风格、分辨率或菜单不能重置游戏进度。

三、背包与真实数据库
1. 背包至少 12 格、至少 6 种有实际用途的物品，覆盖可堆叠消耗品、任务物品和可装备物品。至少一个装备槽与两个快捷槽。
2. 实现拾取、数量反馈、选中与详情、拖放换位/合并、使用、装备/快捷绑定，以及丢弃确认或关键物品保护。
3. 完整处理空背包、容量已满、堆叠上限、不可用/冷却中等情况。UI 显示、物品实际效果和数量消耗一致。
4. 使用本地 SQLite 实际保存背包/装备、玩家、任务、关卡对象状态与设置。表结构和内部组织自行设计；JSON 可以作配置与导出，不能替代数据库。
5. 首次运行自动初始化；存档使用 user:// 的独立目录。继续游戏实际读取数据库，退出进程后重开也能恢复。
6. 背包与已拾取对象/已开宝箱等数据一致提交，不能通过读档或切换维度复制物品。使用绑定参数及必要的数据约束，处理数据库错误与基础版本信息。
7. 坏存档有明确提示和恢复/新建路径，不静默丢弃用户数据。提供存档位置与核验说明。
8. 本题提供 SQLITE_DEPENDENCY.zip：官方 godot-sqlite v4.6，已在 Godot 4.5.1 Windows x86_64 验证数据库创建、绑定参数、事务提交/回滚与关闭重开。将其中 addons/godot-sqlite 放入你的工程；随包保留来源与许可证，可使用附带 README 查阅接口。

四、玩家 UI 必须完整
UI 的配色、字体、图标、布局、控件形态与动效自由设计。考核信息层级、可读性、一致性、真实反馈和导航闭环。
至少提供：
- 主菜单：新游戏、按真实存档状态启用的继续、设置、退出/返回。
- HUD：生命/资源、技能冷却、主目标、快捷栏、交互与拾取/受伤提示。
- 背包：格子与容量、数量、选中/悬浮/拖拽、详情和实际操作入口。
- 任务与地图：实际目标进度、当前位置/方向及已发现关键地点。
- 暂停与设置：继续、检查点重试、返回主菜单、实际生效并持久化的音量/显示或玩法选项。
- 失败与通关：明确状态、重试/返回，以及基于真实数据的结果统计。
- 一致的弹窗确认/取消、返回与输入焦点规则。
所有界面均需有可用入口与返回路径，空/满/禁用/选中/冷却/错误状态应给出反馈。菜单、背包与弹窗的输入不能穿透为世界攻击或技能。适配 1280×720 与 1920×1080；低分辨率游戏画面与清晰 UI 独立处理。
种子、性能、诊断和取证属于独立调试入口，不以调试侧栏代替玩家界面。

1. 附录 A 是本题必做的完整渲染技术基线，与游戏系统同为交付要求，不能只按“有草、有风、能换色”完成。必须交付实际运行的 spatial/canvas_item 草地 Shader 及相关资源；算法、节点与文件组织可自行设计。
2. 附录效果必须进入原生 2D/3D 的实际可玩关卡。可以另设调试验收区域，但不得把完整草地效果只放在独立实验场，主游戏使用明显简化或不交互的背景。
3. 玩家、敌人、技能/物体需接入共享风场与交互系统。切换维度和三风格时保留草场布局、相位、交互历史及游戏状态。
4. 草地 Shader、游戏系统与 UI 均从空白工程开始实现；阶段性技术验证完成后集成到同一可玩关卡。全部基线须以本题实际运行的实现和证据验证。

6. 交互、技能、受击、拾取和 UI 有适度的视觉与声音反馈，音量设置确实生效。具体演出方式自行设计。
7. 优先完成并验证草地技术基线，再扩展玩法与其他系统；最终须对实际可玩关卡的六组合重新验收，记录集成前后表现与性能，避免集成后效果退化。

六、自主创意
至少提出并完整实现一项服务主循环的小机制。可以围绕草丛感知、风向寻路、物品组合、维度线索、互动生物等展开，也可以另行原创；这些例子不要求全部制作。

附录 A 草地 Shader 完整技术基线（必做）
以下技术要求完整适用于实际可玩关卡及验收区域。画面目标为精致独立游戏所需的草簇组织、色块层次、自然交互和成片翻滚。具体美术、草种、调色与实现算法由你自行设计；UI 样式、布局和维度转场保持创作自由，功能与可读性要求保持。

## 一、3D / 2D 双向兼容

1. 实现两条原生路径：3D 使用 Node3D 与 spatial Shader，2D 使用 Node2D 与 canvas_item Shader；提供界面切换。正交或俯视的 3D 场景不能计作原生 2D 实现。
2. 共享草场布局定义、seed、时间、风场、交互轨迹和风格参数。明确 3D 米制 XZ 与 2D 像素 XY 的换算，使风向、交互半径和传播速度具有一致含义。投影、光照和遮挡规则可各自适配。
3. 3D 提供正交主视图和透视检查视图；2D 提供俯视或斜俯视视图，角色与草簇的前后遮挡合理。
4. 使用实例化、合批或其他合理的高效方案，支持密度调节。说明草叶与草簇的组织方式，报告实际实例数；切换视角、移动相机或重新加载草场时，布局、色块和随机相位保持稳定。

## 二、草簇造型与交互

1. 形成连续、有疏密变化的草场，具备草簇轮廓、世界空间颜色分区、少量点缀草种，以及与地面相接的草根表现。可采用 sprite/atlas、程序几何或两者组合。
2. 草叶根部固定，顶端响应更明显；弯曲、看板和轮廓补偿需适配对应风格与视角。不得出现根部漂移、矩形透明底片或明显浮空。
3. 提供可用键盘控制的角色和可拖动的影响物，支持至少四个同时生效的交互源，并提供零、单个和多个交互源的测试条件。
4. 物体经过时，草向合理方向被推开或压低，响应位置、半径和移动速度；离开后柔和恢复，支持短暂压草拖尾。停止、快速穿越、交叉经过和移除影响源时，不出现残留或恢复突跳。
5. 2D、3D 和三套风格中均保留交互；提供交互方向、强度和影响范围的诊断视图。

## 三、像素滤镜专项优化

1. 游戏画面采用固定 16:9 构图，支持 **320×180、640×360** 内部视口，并提供 **1280×720** 高清检查条件。低分辨率画面按整数倍 nearest 放大，调试 UI 独立以清晰分辨率绘制。
2. 三种风格都支持像素滤镜开关。提供有限色板预设、抖色和描边的独立控制，记录实际启用的处理方式；草簇、角色与环境的像素尺度协调。
3. 针对低分辨率调整草簇轮廓、覆盖、透明采样和远景细节。正交 3D 与原生 2D 提供像素对齐方案，并处理风摆时面片变薄、轮廓丢失和细叶闪烁。
4. 抖色、颜色分区、笔触及噪声使用合适且稳定的坐标锚定。相机缓慢移动时，避免明显纹理游移、抖色爬行、色带跳动和采样模糊。
5. 提供连续动画与 **8fps、12fps** 分相动画。低帧率模式中各草簇错开更新相位：单簇具有明确动画节奏，整片草场保持连续运动观感。
6. 验证静止、相机慢移、弱风、强风、角色穿越及远近视角。交付连续镜头；静态截图不能代替像素动态稳定性的验证。

## 四、三套风格化表现

同一个实验场提供以下三套可辨认的预设。切换后保持草场布局、交互能力和时间状态，并同步调整草地、地面、参考物与水面的美术表达。

| 预设 | 必须能观察到的表现 |
|---|---|
| 像素草地 | 清晰草簇 sprite/轮廓、有限色板、成片色块、点缀草种、适合像素画面的动画节奏 |
| 三渲二 / Cel | 可读的明暗阶、受控的软硬边界、轮廓与色块组织、逆光表现；3D 使用非写实着色，2D 遵循对应的配色与轮廓规则 |
| 水墨 | 墨色浓淡、笔触轮廓、干笔断续、纸张纹理、局部晕染与留白；笔触稳定，草场层次、风和交互仍清楚可见 |

水墨需要物体表现与画面处理配合，全屏灰度或统一模糊不足以满足要求。三渲二需要完整的受光与形态表达，只有颜色变化不足以满足要求。描边应保留草场块面，避免每根草的高频黑边破坏画面；像素水墨要保留网格内的笔触层次。

## 五、云影、草场翻滚与环境

1. 实现三层运动：有明确方向与传播的大尺度风阵、中尺度草簇弯曲、局部叶尖摆动。通过受光、法线或色块变化，形成能在连续镜头中辨认的草场翻滚。
2. 风阵传播速度与方向可调。关闭风阵、局部扰动或全部风时，对应运动确实停止；根部保持稳定，运动具有空间相关性。
3. 草地、地面和参考物共享世界空间云影，结合光照方向与物体高度保持关联；原生 2D 采用适合该场景的高度或遮挡适配。镜头移动时云影不跟随屏幕漂移。
4. 场景包含起伏草坡、弯曲土路、少量树木与岩石、小水面，草场与风阵是画面主体。3D 提供与风格协调的环境光/HDRI 和雾；2D 提供相应的光色与远景层次。
5. 水面保留水深层次、岸线、动态水影与交互涟漪。3D 验证场景倒影、折射、接触泡沫和水下焦散；2D 采用匹配自身空间表达的水面效果。各风格下与草场协调，水影不遮盖草地质量问题。


## 六、调试与确定性取证
1. 六组维度×风格均提供全景、草簇近景、交互、水影和逆光检查；切换后显示准确状态。
2. 独立调试入口实际控制：维度/风格、三档分辨率、像素滤镜、色板/抖色/描边、密度、风向/风力/传播速度/动画fps、交互数量/半径/恢复时间、云影/光照和水面效果。
3. 提供风场、局部扰动、草簇分布与色块、交互方向/强度/范围、云影及像素轮廓诊断；可分别隔离效果，不能用同时改动多个变量的素材冒充单项A/B。
4. 场景视觉使用统一可暂停、步进、跳转、复位的仿真时间（bench_time或等价定义），默认seed=20261011。有历史的压草、拖尾或反馈纹理支持清空与重放，并记录键盘/拖拽等手动输入历史；暂停与时间跳转不能让手动状态被默认演示轨迹覆盖。
5. 游戏进行时视觉时间与实际仿真同步。暂停/跨维度/读档后，视觉与角色、敌人、物体状态保持关联；菜单仍能操作，必要的UI动效与场景取证分开记录。
6. 导出无UI原始场景图、带UI图和状态JSON，记录维度/风格、seed、仿真时间、机位、内外分辨率、效果参数、实际草簇数/叶片数、引擎/后端/硬件、实现文件及依赖资源SHA-256。

## 七、渲染专项真实运行证据
1. 六组主要预览各至少5秒真实连续运行，能看见风阵与交互；另提供慢移、恢复与滤镜/云影/风阵/局部扰动分别开关的同状态对照。
2. 分别检查静止、弱风、强风、相机慢移、角色/敌人快速穿越与近远视角，避免只选择静态画面或最有利机位。
3. 连续/8fps/12fps分相须提供足以分辨单簇更新时刻与簇间相位的记录。记录实际采样率和时间戳；确定性逐步重放可以作为辅助证据，但不能替代墙钟真实运行或推导实际帧率。
4. 移动可辨认参考物并改变视角，验证3D倒影与真实场景的对应；折射、泡沫和焦散应与水深/岸线/水下几何相关。固定树石遮罩、任意屏幕UV翻转、与场景无关的静态贴图不能代替要求的场景倒影。
5. 实际操作维度/风格与调试控件，检查全部Shader编译和运行日志。独立性能采集仍按正文执行，不与截图或编码并行；导入成功、截图有变化或源码有函数均不能单独作为效果达标证明。
6. 允许参考与复用开源部件，记录来源、固定版本、许可证与本题适配；相关资源必须随工程打包，运行不依赖网络。
