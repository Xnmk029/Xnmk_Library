# Harness2 架构与当前工作区 Bench 适配分析

分析日期：2026-10-19。上游：google-research/harness2，核对版本 `1cfe254e8d25b15f37048c3730134686abe60335`。源码归档、下载哈希和读取位置见同目录 `SOURCE.json`。本次只做源码和现有工作区分析，没有安装上游运行环境、调用其模型或改动现有 Bench 题面与成绩。

## 结论

Harness2 值得作为独立的增强实验轨道引入。对当前工作区，最有希望先改善工具调用可靠性、复杂任务的完成率和交付验证覆盖；原生 3D/CAD 的轮廓和曲面质量仍需要强的视觉反馈与几何检查，不能仅靠更多反思保证提升。

收益必须分成四类观察：作品质量、交付成功率、执行效率、生成程序的实际运行性能。它增加执行和编辑预算，因此最终一次作答的步骤减少，不代表从初次任务到最终交付的总耗时或费用减少。当前模型、MCP、Godot、Blender、FreeCAD 均没有得到本地 Harness2 对照实测，本文不给预测提升百分比。

## 1 项目架构

### 1.1 角色与数据流

固定权重的执行模型 Solver 在当前任务上产生基线记录。Editor 读取任务、基线执行轨迹和已有经验，分别提出通用流程候选 INV 与领域候选 DOM。两个候选在同一任务上实际执行；Composer 对照轨迹、产物和 harness 差异，合成后继 harness；Solver 再用它执行一次。任务结束后 Reflector 把有证据支持的经验写入库。评分属于独立后处理，不作为这轮提案和合成的标准答案反馈。

在 `k=1` 时，直接采用单个最终合成版本，绕过额外 Selector 会话。`k>1` 时，Selector 对匿名化产物作选择，返回既有候选而非重新创作。最终采用不表示它已被证明最优；这点在没有标准答案时尤其重要。

对应源码：

| 层 | 主要文件 | 职责 |
|---|---|---|
| 命令入口 | `harness2/cli/run_sweep.py`、`judge.py`、`report.py` | 运行、事后评分、汇总分离 |
| 执行契约 | `core/spec.py` | BenchmarkAdapter、RunView、任务和环境描述 |
| 递归与预算 | `core/recursion.py`、`ledger.py` | INV/DOM、合成、并行/串行与预算核对 |
| 改进模型会话 | `core/proposer.py`、`prompts.py` | 调用 Editor、Composer 等，读取文件形式证据 |
| 证据上下文 | `core/context.py` | task、source、trajectory、deliverables、diff、library |
| harness 表面 | `core/tree.py` | 可编辑路径、长度限制、Python 语法和引用校验 |
| 选择与反思 | `core/selection.py`、`library.py` | 匿名选择，记录适用情境、经验、证据 |
| 调度与恢复 | `core/schedule.py`、`runmark.py` | 同领域顺序、跨领域并发、完成标记和配置指纹 |
| 执行器适配 | `substrate/opencode.py`、`substrate/codex.py` | 把同一逻辑映射到两套 Agent 运行时 |
| 数据集适配 | `benchmarks/jobbench.py`、`lab.py`、`workbuddy.py` | 任务发现、运行、证据提取和独立评分 |

`BenchmarkAdapter` 明确要求 tasks、domain_of、task_prompt、task_files、execute、delivered、trajectory、deliverable_text、base_harness、validate_tree、score 等接口。RunView 只承载运行、交付、费用等信息，不承载分数。选择器还有白名单化的 `deliverable_assets` 扩展，可以提供图片证据；当前工程文件仍需自己的提取和验证适配器。

### 1.2 可编辑的八类组件

| 组件 | 作用 | 对工作区的可迁移例子 |
|---|---|---|
| 系统提示 | 执行方法和角色 | 先建立可检查产物，再逐步完善 |
| Guardrails | 操作约束与完成条件 | 读取失败日志后再换方案，停止无效重复 |
| Memory | 常用事实与环境知识 | 版本差异、坐标/单位约定；需按环境分开 |
| Tool guidance | 工具调用说明 | 同步与异步作业、超时、返回错误语义 |
| Subagents | 分工角色 | 独立检查与研究；使用仍受宿主授权和能力约束 |
| Skills | 按需读取的领域流程 | CAD 形状有效性、Shader 编译与场景检查 |
| Scripts | 确定性辅助程序 | 测量、批处理、导出、结构检查 |
| Plugins / hooks | 工具循环内的机制 | 长时间无文件落盘提醒、错误回传与检查点 |

八类是逻辑划分，两个运行时的物理文件布局不同。OpenCode 使用四个常驻 Markdown 文件、skills、sub_agents、scripts、plugin；Codex 将常驻指导放入 AGENTS.md，按 `.agents/skills`、角色、scripts 和 `.codex/hooks.json` 等实际接口接入。源码对常驻内容设字符上限，对技能触发、引用路径、部分脚本和 hooks 结构做校验。其校验不能证明任意生成脚本在语义上安全或正确。

### 1.3 两层递归

- 任务内：反复调整当前任务的执行方式。
- 跨任务：更新改进者可查询的经验库。下一题仍从共同的基线 harness 开始，旧经验供提案者选择和改造，而非把上一题整套定制状态无条件继承给执行模型。

经验条目含可执行 harness 和 EXPERIENCE.md，至少要求 cue、lesson、evidence；没有可支持的经验时不新增条目。同一领域按任务顺序推进，只读取先前条目；不同领域可以并发。库须按实验配置分开。这是可审计的文件库，并非在线更新模型权重，也不是实现了普适自动知识管理。

## 2 性能提升如何实现

### 2.1 对照可执行修改

INV 针对规划、调用、上下文、重复操作等跨任务缺陷，DOM 针对当前领域程序和约束。两类候选都要实际执行，再以行为变化支持合成。被采用的组件可以是一个脚本或技能，也可以是多项协同修改；不是只让同一个模型在原答案上口头检查一次。

### 2.2 将可重复工作外置

脚本可把机械提取和检查从多次模型调用转为确定性步骤；技能按需读取，避免常驻上下文无限膨胀；插件和 hooks 可以把检查、提醒置于工具循环内。收益主要来自少遗漏、少误用、早发现失败，以及把预算投入有效动作。

这些收益不自动等于执行速度提升。更完整地验证或补齐交付可能需要更多调用。生成程序本身的 FPS、渲染帧时间和数值性能也需要固定 workload 另测。

### 2.3 从改进过程提炼经验

库保留为何改、改了什么、何种行为得到改善，而不是只有一次作答结论。对软件操作任务，可迁移的是版本兼容、失败识别和检查方法；某只鼠标的轮廓数据、某张视觉题的答案、某道题的隐藏评分细项不适合作为泛化经验注入后续受测任务。

### 2.4 官方结果的边界

论文采用 Gemini 3.5 Flash 和 GLM-5，分别搭配 OpenCode、Codex；论文主实验的默认改进者为 Claude Opus 4.8。当前代码的 `HARNESS2_IMPROVER_MODEL` 未设置时则回落为执行模型，不能把安装后的默认配置与论文配置混为一谈。单步相对基线的最大收益为：WorkBuddy 平均分 +11.5 分、JobBench +4.5 分、LAB Partial +11.8 个百分点。不是统一的相对百分比，也不是当前 GPT、DeepSeek、Kimi 或原生建模任务的实测结果。

一个具体例子是 GLM-5 / OpenCode 的 WorkBuddy 平均分 64.2→75.7。工具可靠性例子中，Gemini / OpenCode 的 JobBench 工具错误率 14.4%→9.1%，同时调用数 27.4→32.8。这说明质量和可靠性收益可能伴随更多执行。

论文也报告了误选更弱候选、共享错误假设和执行波动造成的回退。对原生建模，这些风险对应“英雄图更好看却曲面更差”或“多个候选都沿用同一错误轮廓假设”。

### 2.5 实际预算

`core/ledger.py` 明确规定每任务、每模式：

`R = 4k` 次执行：k 次基线 + 2k 次候选 + k 次最终合成执行。

`P = 3k` 次改进阶段：k 个 INV + k 个 DOM + k 个 Composer。

| k | 完整执行 | 改进阶段 | 另计 |
|---|---:|---:|---|
| 1 | 4 | 3 | 反思、失败重试；无额外 Selector |
| 5 | 20 | 15 | 选择、反思、失败重试 |

一次 rollout 或编辑阶段内部可有很多模型/工具调用，不能把上述次数当作 API 请求数。并行和顺序模式使用相同计数预算；前者扩大探索宽度，后者在前一轮上继续细化。并行收益受 CPU、GPU、内存、原生程序隔离和额度制约。总成本须包含全部执行、编辑、选择、反思、重试和渲染验证。

## 3 当前工作区的覆盖情况

本次按各一级目录下直属项目的 PROJECT_PROMPT.md 盘点：L1 8 项、L2 15 项、L3 21 项、L4 13 项、Image 15 项、NativeWorkflowBench 10 项，共 82 个题面入口。这里含语言、输入条件和续作变体，不等于 82 个独立题型。

Backend/BANK.json 有 8 个 active 条目，均映射到现有 L1–L4 项目，不再重复加 8。Vision/catalog/BANK.json 有 416 条记录，含历史副本、共享图、待校准与非计分项，不能当作 416 道独立题；其中 PairedVision 为 8 条条件。另有冻结 r6 的 Agent CLI 专项，其协议需单独处理。

逐项目映射见同目录 `BENCH_MATRIX.csv` 和 `WORKSPACE_INVENTORY.json`。以下高/中/低表示值得试验的优先级和适配判断，不是实测涨幅。

| 任务族 | 相关范围 | 潜在收益与实现方式 | 限制 |
|---|---|---|---|
| 后端与工程逻辑 | Backend B01–B08、DeepSWE、持久化/并发题 | 优先级高：重现失败、开发公开行为测试、日志取证、恢复与导出流程 | 不把隐藏验收或金标送入改进者；正确性不能由自检替代 |
| 网页与交互应用 | L1–L3 的网页、游戏、展示与交互题 | 中高：真实浏览器操作、状态与导出检查、局部截图对照、离线验证 | 静态漂亮不等于交互正确；错误优化目标会把预算花在装饰上 |

| 文档/表格/长文本 | WeChatCheckinExcel、报告类及 LitRPGNovel | 中高：确定性统计、资源打包、布局/一致性检查 | 当前题型与论文办公任务并不相同；创作审美仍需独立评审 |

尚未形成正式独立题面的“枪械建模—Godot 动画、室内工装、产品设计全流程”等规划，不计入 82 个已发现题面入口。它们预计更需要检查点和跨软件状态契约，但只能在明确输入、交付和验收后实测。

## 4 对当前原生建模最有价值的做法

建议先评估三项，不直接从全量 k=5 开始：

1. **让工具失败成为结构化证据。** 记录工具返回、实际进程退出码、traceback、作业状态和文件落盘；这些字段分开。当前 DSH 审计已经存在“Python 异常却退出 0／被报告 ok”的修复记录。经验库可以提示识别同类问题，但不能替代修好桥接层的错误语义。
2. **把造型反馈放在正式渲染之前。** 每个候选用同一参考、坐标、六面相机和中性显示生成便宜预览，检查轮廓、拇指凹面和主键位置。改进者读取真实图片与几何统计，而非只读 README。高采样、微纹理和完整视频放在形体稳定之后。
3. **将重开和交换验证固定化。** Blender 检查重新打开的真实数据；FreeCAD 检查重算、有效实体、参数改动和 STEP 导入。它们是公开工程检查，不能宣称为隐藏标准答案或视觉评分。

同一台机器上，不宜让多份 Blender/FreeCAD 重建和 GPU 渲染按默认候选宽度同时争抢资源。可以先并发轻量提案，重型候选执行串行或限流。这样借用的是递归模式，不要求照搬上游的实际并发度。

## 5 接入边界

### 5.1 运行环境

上游文档以 Linux、Python 3.12 为基准，包声明支持 3.12/3.13；Node 20+，部分 Bench 需要 Docker、Pandoc、Poppler。当前工作区在 Windows，FreeCAD 自带 Python 为另一环境，现有部分工具又使用 Python 3.14。不能把它直接安装进这些既有运行时并假设兼容。

可以评估独立 Linux/WSL 控制层加 Windows 原生工作进程，或只移植核心调度到当前 Windows harness。两者都是本地工程方案，不是上游已经提供的原生软件支持。Blender、FreeCAD、PS、SketchUp 和 DSH 都需要新的适配层；MCP 工具本身不会因装上 Harness2 自动接入。

### 5.2 与现有 bare 协议的关系

当前 sandbox 协议要求受测方只接收原题面及锁定输入，并禁止 Agent/IDE 状态污染工作目录。上游会挂载 AGENTS.md、技能、脚本和 hooks，不能静默加入既有 bare 成绩。

建议保留两类结果：

- **bare 固定轨**：原题、原工具与固定指导，复用当前记录和规则。
- **harness-enhanced 增强轨**：明确版本化的执行指导、组件白名单、改进模型、预算、库快照与候选谱系。需专门登记允许的组件与挂载位置，独立 run、独立结果，不绕过现有 H2/H3。

辅助程序可以改变“模型自己写出算法”与“工具替模型完成工作”的比例。这是系统能力研究的一部分，但须公开，否则无法解释模型之间的排名。

### 5.3 评估隔离与经验泄漏

源码有不携带分数的 RunView、评分后处理、上下文排除和文本标记检查；上游仍明确说明执行器网络不受限，Codex 使用关闭沙箱的模式，验证中甚至出现过自动下载公开 rubric。它不是可直接继承的强隔离评估环境。

本地应由外部权限、输入白名单和网络策略保证：执行器与改进者均看不到私有评分、金标、其他模型答案或留出集结果；评分器和组件编辑器不能相互修改。不能通过修改 transcript 扫描规则，把实际泄漏改成 PASS。

视觉目录有重复图与历史条件，划分训练/验证时应按源图和任务族划分，而非只按任务 ID 随机拆分。同一鼠标不同参考语言版本也不能被当作完全独立的迁移验证。

## 6 建议的验证实验

首批选择有明确检查反馈的三个方向：后端 B02/B05、Godot Shader、FreeCADMouse 或 BlenderMouse 中的一项。选择是试点建议，不是新增派发授权，本次没有启动这些测试。

最低限度设置四个条件：

| 条件 | 要验证的问题 |
|---|---|
| A 固定 bare 单次 | 原始基线 |
| B 固定 harness 的等预算重复执行与相同选择器 | 收益是否仅来自多次尝试和选择 |
| C Harness2 k=1，初始库为空 | 当前任务的可执行修改是否有增益 |
| D 冻结经验库后的新任务 | 经验是否在留出任务上迁移 |

B 与 C 先对齐完整执行预算，还要分别报告编辑/选择/反思消耗；进一步增加同总 token、同费用或同时间上限的实验，避免把“相同执行次数”误写成“相同总成本”。跨模型比较时固定或明确区分改进模型，否则引入了不同外部教师。

保留所有候选和失败，记录任务、输入、环境、工具/插件、harness、库及改进模型的版本/哈希。评分在选择提交后执行，不能用最终隐藏得分决定当前任务选谁或如何改。

每组至少看这些指标：

- 工具实际错误率、超时率、无产物退出率；区分后端故障与模型调用错误。
- 原生重开、编译、交互检查、导出往返等公开工程检查。
- 轮廓/曲面/材质盲评或独立几何指标，不能只看图数和文件存在。
- 全流程总时间、模型 token/费用、所有试跑与渲染时间、峰值内存及显存。
- 若生成程序有性能要求，另以固定硬件、分辨率和 workload 量测中位/P95 帧时间、异常与稳定性。

当前没有足够证据给出“全部 Bench 提升多少分”。优先把工具可靠性与原生验证接入，再验证形体和审美质量是否随之提高，能更快判断这个方法在工作区是否值得继续扩展。
