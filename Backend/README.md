## 选题依据

B 站题最值得继承的是“输入真实发生变化 → 工具执行 → 人立即看到效果”：换一条评论，标签随之变化；反复加载，没有重复标签。推广到后端时，界面承担结果观察和操作入口，正确性由文件、数据库、网络记录和事件历史核验。

这组题从浏览器自动化扩展到真实文件处理、HTTP、状态机、持久化、并发事务与审计。服务界面和静态 HTML 报告均由真实执行结果生成，正确性通过独立 API、CLI、数据库/文件结果与事件记录核验。

已参考现有 [B 站脚本](../L1_Basic/BilibiliUserscript/README.md)、[脚本验收器](../L2_Intermediate/BilibiliIpAcceptance/README.md)、[Archive](../L1_Basic/Archive/PROJECT_PROMPT.md)、[微信导入 Excel](../L1_Basic/WeChatCheckinExcel/PROJECT_PROMPT.md) 和 [工业数字孪生](../L3_Advanced/IndustrialDigitalTwin/PROJECT_PROMPT.md)。新题不重复 Archive 的通用文件整理；不依赖真实微信账号；后端状态也不能像数字孪生演示题一样仅由前端随机数驱动。

## B02 · L1 · 日志时间线与错误定位器

**题面草案：**实现一个本地日志分析工具。用户在网页或桌面窗口中选择 UTF-8 JSONL 日志，程序逐行解析，展示时间线、级别统计、错误列表和原始行定位。解析与统计必须由独立处理模块完成，另提供 CLI 输出相同结构的 JSON；不能只有页面内写死的数据。

**公开契约：**每行包含 `timestamp`、`level`、`service`、`message`，可选字符串 `request_id`。时间采用带时区的 RFC 3339，比较时转换为 UTC；合法级别为 DEBUG/INFO/WARN/ERROR。坏 JSON、缺必要字段、非法时间单独列为坏行，不计入合法记录统计。原始行号从 1 开始，重复日志保留，时间相同按行号稳定排序。筛选时间采用左闭右开区间。

**交付：**一个启动入口、可操作界面、CLI、依赖声明和 README。允许 Python、Node.js、Go、C# 等；处理模块不得依赖界面才能运行。界面可用分页，不要求一次渲染全量文本。

**一分钟演示：**导入包含错误和坏行的日志 → 选择 ERROR → 点击一条记录查看原文 → 筛选某个 request_id → 导出当前结果。

**独立验收设计：**

1. 用逐行真值核对合法数、坏行数和各级别计数，不能吞掉坏行后声称全部成功。
2. 两种时区表示同一时刻时排序一致；同毫秒日志顺序稳定；区间终点不被包含。
3. 相同 message 不同 request_id 不能错误合并；连续两行完全重复仍计两条。
4. 包含 `<img ...>` 的 message 只作为文本，查看原文不执行 HTML。
5. 同一文件的 CLI 输出与界面导出语义一致；输出保留行号、原时间和原消息。
6. 公开压力档为 100,000 行、总大小不超过 50 MiB；记录峰值内存和耗时，不在未校准机器上设统一毫秒门槛。

**典型失败：**用字符串直接比较时区时间；把坏行悄悄跳过；一次异常终止整文件；界面统计与导出不同。

## B03 · L2 · 本地文件搜索与增量索引

**题面草案：**实现限定工作目录内的文件搜索服务和界面，索引 `.txt`、`.md` 文件。支持文件名与正文的字面子串搜索、命中片段、索引进度；新增、修改、改名、删除后更新结果；重启服务仍可搜索已提交的索引。

**公开契约：**根目录由启动参数指定。索引 UTF-8 文件，单文件最大 1 MiB，超限或解码失败要记录跳过原因。路径以相对根目录形式输出；符号链接和 Windows junction 不跟随。查询为区分大小写的字面子串，不是 SQL 或正则；结果按相对路径排序。允许文件监听或轮询，但正常变更在 3 秒内可见，压力下用队列进度明确表示未完成。提供显式全量重扫以修复漏掉的文件事件。

**交付：**后端、持久化索引、搜索界面、启动/重扫入口、README。可使用 SQLite FTS 等索引库，但本题规定的查询语义必须保持。根目录外的内容不能被搜索或预览。

**两分钟演示：**搜索“断点续传” → 新建含该词的文件 → 看到新命中 → 改名 → 删除 → 重启并再次搜索。

**独立验收设计：**

1. 测试夹具同时包含中文、空格文件名、同名不同目录和不可解析文件；与直接扫描的真值比较。
2. 修改前后文件大小相同，且修改时间被恢复，执行全量重扫后仍必须发现内容变化。
3. 连续新增/改名/删除并重扫后，不残留旧路径、不出现重复命中。
4. 服务在索引批次中被终止；重启后结果来自完整提交状态，能够继续重建。
5. API 直接请求 `../`、绝对路径及通过链接指向根外的路径，均不能读出根外内容。
6. 禁止通过只修改页面列表来模拟索引更新：关闭界面，继续修改文件，再由独立 API 请求验证。

**典型失败：**只用 mtime 判断变化；路径参数直接拼接；重启后索引丢失；文件删除后搜索仍命中。

## B04 · L2 · Webhook 收件箱与重放工具

**题面草案：**实现本地 Webhook 调试服务。接收事件，显示原始请求、验签结果、去重状态；通过界面将已接收事件重放到受控的本地接收端，保留每次投递的状态码、耗时和错误。

**公开契约：**`POST /hooks/{source}`；事件 ID 为 `X-Event-Id` 字符串，签名为 `X-Signature: sha256=<小写十六进制>`，按预置 source 密钥对原始请求体计算 HMAC-SHA256。验签通过后才解析 JSON。首次合法事件返回 201；同 source、同 ID、相同原始字节重试返回 200 且不新增事件；同 ID 不同字节返回 409；验签失败返回 401。重放只发送到启动时配置的本地夹具 URL，不接收任意目标 URL。请求体限制 1 MiB。

**交付：**服务、事件列表和详情界面、重放入口、持久化数据库、签名请求发送示例。重放保留原始请求体和事件 ID；投递尝试有独立 ID，不重新创建收件事件。

**两分钟演示：**发送一次有效签名请求 → 再发同 ID 请求 → 发无效签名请求 → 对已接收事件点击重放，让接收端先返回 500、再返回 200 → 展开两次尝试记录。

**独立验收设计：**

1. 改动 JSON 空格但不重签必须失败，防止对解析后 JSON 验签。
2. 20 个并发重复事件只持久化一条；不同 source 的相同 ID 分开保存。
3. 同 ID 不同请求体明确冲突，不静默覆盖已有事件。
4. 两次重放留下两条实际接收记录，与界面的状态和请求体哈希一致。
5. 重启后收件与投递历史保留；密钥不出现在 API 响应、界面和导出记录。
6. 接收端超时和 500 可区分；超大请求被拒绝，不显示“成功接收”。

**典型失败：**验签对象不是原始字节；内存去重；界面显示投递成功但接收端没有收到；把重放计为新事件。

## B05 · L3 · 大文件断点续传工作台

**题面草案：**实现文件上传服务和工作台。将文件分块并发上传，显示每块状态；刷新浏览器、终止服务或中断连接后恢复；仅补传缺块，最终提供可下载文件和 SHA-256 校验结果。

**公开契约：**创建上传会话时提交文件字节数、块大小和整体 SHA-256，返回独立 upload_id；块编号从 0 开始，除末块外大小固定，每块附 SHA-256。查询会话返回已提交块集合。相同编号、相同内容重复上传幂等；不同内容返回 409，不能覆盖已确认块。全部块校验成功后原子发布成品；下载接口在发布前不可读到半成品。文件名仅是显示信息，落盘路径不能由用户文件名直接决定。

**交付：**上传/查询/合并/下载 API、界面、持久化状态和故障恢复说明。客户端选回同一文件时验证其身份，不能把另一文件的后半段接入旧会话。

**两分钟演示：**上传 64 MiB 固定种子文件，块大小 1 MiB → 中途暂停并重启服务 → 重新选择同一文件续传 → 下载并比较哈希。展示实际传输字节，不能只让进度条接着动。

**独立验收设计：**

1. 分块乱序、重复和并发到达后，成品逐字节一致。
2. 向一块注入损坏数据，必须拒绝且状态不能计为完成。
3. 在块落盘、状态提交、成品发布的边界中断进程；恢复后已确认块可复用，状态不会谎报完成。
4. 重试合并请求只能发布同一份结果；下载永不返回部分文件。
5. 用独立网络记录确认恢复后只补传缺块；不把重传整个文件包装成断点续传。
6. 0 字节文件、非整块文件、同名不同内容文件及路径穿越文件名都有确定行为。

**典型失败：**仅浏览器内保存进度；重复块损坏输出；先返回成功再落盘；合并时读入整个大文件导致资源失控。

## B06 · L3 · 后台任务队列与失败恢复看板

**题面草案：**实现一个持久化任务队列，至少支持两个独立 worker。任务对指定夹具文本文件计算 SHA-256 并发布结果文件；界面显示排队、执行、重试、成功、永久失败及每次尝试。支持延迟任务和任务去重，worker 被强制终止后由其他 worker 恢复执行。

**公开契约：**任务用字符串 job_id 和幂等键识别。重复提交相同键和相同参数返回原任务，不同参数返回 409。采用至少一次执行语义；领取带租约和递增 fencing token，结果提交必须持有当前 token。允许重复计算，但最终结果和成功记录只能有一份。可重试失败最多执行 3 次，等待 1 秒、2 秒；参数错误直接永久失败。测试时钟可控，执行时限与租约参数公开。

**交付：**API、持久存储、可单独启动的 worker、看板和重启演示命令。可用数据库实现队列；不可直接套用成熟队列框架完成核心调度状态机。结果内容必须来自实际文件计算。

**两分钟演示：**提交一批任务 → 终止正在工作的 worker → 看到租约过期与接管 → 恢复旧 worker → 观察旧尝试的提交被拒绝，最终结果只保留一次。

**独立验收设计：**

1. 并发领取时，同一个有效租约不能被两个 worker 同时拥有。
2. worker 计算后、提交前崩溃；重新执行后只出现一次有效发布。
3. 暂停 worker 直到租约过期，接管后再恢复旧 worker，旧 token 不能覆盖新结果。
4. 相同幂等键并发提交只产生一个任务，服务重启后仍成立。
5. 暂时性错误、永久性错误分别走正确重试路径，尝试次数和等待顺序可核验。
6. 独立读取产物哈希和状态历史；界面显示 succeeded 但产物不存在视为失败。

**典型失败：**宣称“只执行一次”却没有处理崩溃窗口；用内存锁代替跨进程互斥；旧 worker 覆盖接管后的结果。

## B07 · L4 · 离线协同文本编辑器

**题面草案：**实现两个浏览器客户端可协同编辑的纯文本笔记服务。客户端断网后仍可编辑，重连同步；服务重启后已确认操作保留。提供编辑区和操作历史视图，清楚区分本地待同步、服务已确认和远端已接收状态。

**公开契约：**范围仅限纯文本插入与删除，不要求富文本、多人光标或账号体系。每个操作有稳定 client_id、单调序号和因果上下文；重传同一操作不能重复应用。以 Unicode 码点为基本单位，不能拆坏代理对。同一锚点的并发插入必须按公开且确定的规则排序；删除只能删除操作创建时可见的目标字符，不能吞掉未见过的并发插入。选用 CRDT 或 OT，但需公开完整冲突语义，并实际实现核心合并逻辑。

**交付：**可开两个独立浏览器上下文的编辑器、同步服务、持久操作记录、断连控制和导出功能。可以使用 WebSocket 库，不允许直接把完整协同引擎当作核心实现。离线操作须持久化到客户端，刷新后仍可同步。

**三分钟演示：**A、B 打开同一笔记 → 断开 B → 两边在同一位置编辑并删除不同内容 → 恢复连接 → 看双方收敛及操作来源 → 刷新两边并重启服务复核。

**独立验收设计：**

1. 并发插入不丢任一方内容，结果满足声明的确定性排序；不能只比较“两边一样”。
2. A 删除旧字符、B 在邻近位置插入新字符，重连后保留未被观察到的新插入。
3. 相同操作重复投递、乱序投递后，去重和因果依赖正确；用固定操作历史验证最终文本。
4. 在收到服务确认后终止服务，重启不能丢失已确认编辑。
5. 离线刷新客户端后仍保留未确认操作；再次同步不会重复字符。
6. 对随机生成的合法操作序列，用独立参考语义核验收敛和内容保全；包括中文和非 BMP 字符。

**典型失败：**最后一次整篇覆盖导致另一方编辑丢失；界面相同但数据都丢了；只用 localStorage 在同浏览器标签间同步伪装网络协作。

## B08 · L4 · 三节点键值服务与故障演练台

**题面草案：**实现三个独立进程组成的持久化键值服务，以及展示角色、任期、复制进度和请求结果的演练台。支持 put/get/delete，停止当前主节点后重新选主；网络分区时少数派不能确认写入，恢复后自动追平。

**公开契约：**固定三节点，不要求动态成员变更、拜占庭容错或跨地区部署。采用 Raft 或其他明确满足本题语义的共识方案；实现核心选主、日志复制和恢复，不能直接调用现成共识服务。写入成功表示已在多数派持久化并提交；相同 request_id 重试幂等。读取必须满足线性一致性，无法确认安全读取时返回不可用，不能由失去多数派的旧主返回成功的陈旧值。客户端超时表示结果未知，可凭 request_id 查询或重试，不能当作必然失败。

**交付：**三个真实节点、独立数据目录、客户端 API、可观测界面和受控故障代理。停机与分区由评测器或外部进程实施；界面上的“断开”按钮必须映射真实连接故障。资源档建议 3 节点、3 客户端、1,000 次操作、值大小不超过 4 KiB，最终阈值需在固定机器上校准。

**三分钟演示：**写入键值 → 停止主节点 → 新主接管 → 隔离一个节点并向它请求写入，显示不可用 → 多数派继续服务 → 恢复隔离节点并比较已提交状态。

**独立验收设计：**

1. 任意已确认写入经历一台节点故障后仍可读，不能依靠浏览器缓存回显。
2. 1+2 分区下，单节点一侧不得成功提交写入；两节点一侧可以在选主完成后继续。
3. 隔离旧主后，它不能提供声称线性一致的陈旧成功读取。
4. 日志写入和响应确认边界崩溃，恢复不丢已提交数据，未提交后缀正确处理。
5. 相同 request_id 跨选主重试不会重复产生状态效果；冲突参数有确定拒绝规则。
6. 采集调用/返回时间、请求 ID、返回值和超时记录，独立执行有界历史的线性一致性检查；最终三份数据相同不是充分证据。

**典型失败：**三个状态卡片实际共用一个内存 Map；主节点切换只改 UI 标签；少数派照常写；只比较最终快照而遗漏中间错误读取。

## 统一验收和派发建议

新增 B02–B08 建议每题 100 分：核心结果 40、异常与边界 25、重复/重启等题内状态语义 20、可操作演示 10、可复现交付 5。B01 保留现有冻结权重，不能用此方案重算历史分。每题正式发布前需把这些分数组落实到独立断言，不按页面漂亮程度或代码行数代替功能评分。

每题至少准备正常、边界、故障三类合成夹具，并校准三种不同错误实现。夹具必须来自评测者；模型自带的自测和样例只作补充。正式派发包包含完整题面、协议、公共小样和资源限制；独立评测包包含金标、随机种子、隐藏参数和反例。隐藏的是参数，不是题面没有说过的要求。

界面验证用真实指针操作；后端验证关闭界面后直接调用 API/CLI；证据保存输入哈希、操作历史、最终产物、运行时版本、截图和结构化报告。禁止把“页面出现成功文字”当作服务真实完成。进程终止、网络中断由外部控制，不能由被测实现自行声称故障已经发生。

新题允许安装锁定版本的第三方依赖；准备完成后的演示与评分只使用本地合成数据及受控服务。不能把 B01 的“禁止一切主动请求、禁止持久化”机械推广到后端题。语言与框架可选，但正式比较需冻结运行环境和相同资源预算。

建议落地顺序：先补强 B01 自动验收，再实现 B02、B04、B05 的公共夹具与评分器。这三题分别覆盖文件解析、HTTP 状态处理和中断恢复，演示直观、环境依赖少；B07、B08 留作 L4，先冻结冲突/一致性语义再派发模型。
